# IT采购寻源地图

把用户的一次需求文档输入，自动转成“需求理解 → 五看实时寻源 → 供应商分布地图 → 采购短名单”的完整交付。复用当前对话已有信息，不要求用户重复输入流程提示词。

## 固化默认任务

将以下任务视为用户上传或粘贴需求文档后的默认指令，自动执行，无需用户重复输入：

> 确认的需求边界，开始寻源。请按华为五看做实时行业、竞品、同类客户路径、技术路线、合规风险和行业玩家调研；保持市场扫描原有三段结构，并生成供应商地图 HTML。

除非用户明确说“只解读需求，不要寻源”，否则不要停下来询问是否继续寻源。

## 自动工作流

### 1. 读取需求文档

- 读取用户上传或粘贴的全部需求内容，包含正文、表格、附件中可读取的批注和关键字段。
- 优先使用当前环境可用的文档读取能力；保留原文中的数字、单位、日期、范围和约束。
- 仅在文档无法读取，或连采购品类都完全无法识别时，提出一个阻断性问题并暂停。其他缺口一律标为“待确认”，继续完成后续流程。

### 2. 内部完成需求理解与边界提取

提取并区分文档已明确内容与待确认内容：

- 业务问题与期望结果
- 项目目标
- 范围内与范围外
- 用户、角色、数量、并发或业务规模
- 功能和关键业务流程
- 现有系统、接口、数据流与迁移
- 部署模式、基础设施和运维边界
- 数据分类、数据位置、安全与合规要求
- 预算、采购模式和商业约束
- 时间计划、里程碑与上线要求
- 成功标准、验收口径与 P0 要求
- 信息缺口、矛盾点和可能影响寻源的假设

不要补默认预算、规模、SLA、合规等级或技术参数。文档未写明时使用“待确认”，但不要因此等待用户确认。

### 3. 形成研究边界

- 将需求归入足够具体的采购品类或技术领域。
- 根据文档限定地域、研究时点、客户规模、部署模式、行业属性、数据敏感性、预算信号和交付边界。
- 把宽泛需求拆成可比较的技术路径、产品型供应商、方案/集成型供应商及必要的替代路径。
- 为行业玩家分布图选择最能区分当前品类玩家的横轴和纵轴。轴必须是与本次需求相关的分析维度，并写明定位依据；不要固定套用通用坐标轴。

### 4. 按华为五看做实时研究

使用当时可用的实时研究能力获取公开证据，优先使用监管机构、标准组织、政府公示、厂商正式资料、公开财报、公开招投标和可核验客户案例；分析师与行业媒体用于补充或交叉验证。

- **看行业**：政策监管、标准、技术范式、产业驱动、供应风险。
- **看市场**：细分方式、采购/部署模式、玩家类型、价格和交付信号、格局变化信号。
- **看客户**：同类客户面对的相似问题、公开采用路径、落地前提、实施与迁移方式。
- **看竞争**：竞品、行业玩家、产品/方案商差异、技术路径、目标客群、部署模式、替代与合作关系。
- **看自己**：需求方现有系统、团队能力、数据与合规约束、迁移/实施/运维承受度，以及各类方案的适配性。

覆盖但不限于：竞品与行业玩家、同类需求常见做法、技术路线、部署模式、接口与数据路径、合规风险、价格/计费信号、交付周期/生态信号、潜在锁定与退出难点。

### 5. 构造有证据的地图数据

在生成地图前，完整读取 [五看与供应商地图数据规范](references/five-looks-and-map-schema.md)，按该规范构造 UTF-8 JSON。

- 为每个来源记录标题、主体、日期、URL 或可定位出处，并赋唯一 source ID。
- 将事实、供应商声明、分析推断、参考材料和待验证项分开。厂商官网或案例中的自述标为 `vendor_claim`。
- 只有存在可回链公开证据、坐标依据及坐标来源的厂商才能进入 `vendors`。
- 证据不足的名字只能进入 `pending_verification_vendors`，不得给坐标，不得当作已验证行业玩家。
- 将每家已验证玩家标为 `shortlist`、`watch` 或 `exclude`，表达当前采购判断，不表达市场排名或绝对好坏。
- 在地图数据中呈现玩家类型、技术路径、目标客群/部署模式、替代关系、需求适配、合规待验证和来源。
- 不能把来源数量或气泡大小解释为市场份额、营收、排名或能力得分。

若没有联网能力或公开证据不足，仍构造并生成“待验证地图”：保持 `vendors` 为空，将未验证线索放入 `pending_verification_vendors`，并明确后续核验动作。不得凭模型记忆填入玩家、能力、客户、市场格局、市场份额或坐标。

### 6. 生成供应商地图 HTML

把地图 JSON 保存到当前任务可写目录，然后运行：

```bash
python scripts/render_supplier_map.py supplier-map-data.json --output "供应商地图-<品类>-<YYYYMMDD>.html"
```

- 以实际脚本所在 Skill 目录解析 `scripts/render_supplier_map.py`；不要假设当前工作目录就是 Skill 目录。
- 修正脚本报告的数据校验错误后再生成；不要为通过校验而编造来源或坐标依据。
- 生成离线单文件 HTML，不依赖外部 CDN、脚本或样式。
- 把 HTML 作为本轮核心附件交付；JSON 仅作生成中间数据，除非用户要求，否则不单独展示。

### 7. 输出聊天报告

结论先行，保持专业、克制的采购语气。对关键判断使用“事实 / 供应商声明 / 分析推断 / 待验证”语义，确保读者能分清证据强度。

完整寻源报告严格只使用以下三个顶层标题，标题文字与顺序不得改变：

```text
【第一段·扫描范围】
【第二段·方法 × 渠道矩阵】
【第三段·市场全景图】
```

不要增加“需求解读”“华为五看”“短名单”“附件”等其他顶层章节。

#### 【第一段·扫描范围】

- 在开头给出需求意图摘要：这份文档要解决什么业务问题、期望什么结果。
- 写清品类、地域、研究时点、范围内/外、规模/用户、系统与集成、部署、数据与合规、预算、时间、成功标准。
- 把缺失或矛盾信息标为“待确认”，并说明其可能影响，不补默认值。
- 把“看行业”问题和“看自己”边界嵌入本段，不另起顶层章节。

#### 【第二段·方法 × 渠道矩阵】

- 用矩阵说明本次实际使用的研究方法、渠道、状态（已用 / 未用 / 待补）和获得的证据。
- 嵌入五看所依赖的政策标准、厂商资料、客户案例、招投标、财报、分析师/媒体、社区或生态等来源。
- 说明来源日期与证据局限；不要把“未查到”写成“没有”。

#### 【第三段·市场全景图】

- 先给采购结论：优先关注的技术路径、玩家类型、主要风险和下一步验证重点。
- 呈现市场切分、玩家类型、行业玩家分布、技术路径、目标客群/部署模式、竞品和替代关系。
- 嵌入看市场、看客户、看竞争和看自己适配结论；给出同类需求采用路径、价格/交付信号、技术趋势及合规风险热区。
- 给出短名单、观察和排除判断。每家写明具体适配理由、证据不足处、风险及建议验证动作；可靠候选不足时如实说明，不凑数量。
- 明确行业玩家分布图坐标是“分析定位”，不是市场排名、份额或客观能力评分。
- 在本段末尾放置生成的 HTML 文件链接，格式为 `[供应商地图 HTML](</绝对路径/供应商地图-品类-YYYYMMDD.html>)`，不要另起顶层章节。

## 特殊分支

仅当用户明确说“只解读需求，不要寻源”或意思完全等同时：

- 只输出需求意图、业务问题、目标、范围内/外、规模、系统/集成、部署、数据、合规、预算、时间、成功标准、缺口与矛盾。
- 不做实时研究，不列厂商，不构造地图 JSON，不生成 HTML。
- 不主动追问非阻断信息；用“待确认”保留缺口。

用户要求补充、换地域、调整边界或继续比较时，复用当前对话中的需求边界、来源与已验证玩家，只研究变化部分，并重新生成受影响的报告与 HTML。

## 质量底线

- 不凭记忆生成厂商、客户案例、能力、价格、份额、格局或坐标。
- 不把供应商宣传当独立事实；明确标注 `vendor_claim`。
- 不用单一厂商来源证明市场格局；需要外部或多源证据。
- 不给无法回链来源和日期的事实性结论。
- 不用伪精确数字填补需求或市场信息。
- 不把短名单写成定标结论；最终选择仍需 POC、演示、客户背调、商务和合规核验。
- 不改变三段式聊天输出结构。
