# IT 市场调研与寻源信息整理

直接完成调研并整合信息。不要输出搜索过程、方法论复述或框架名称。

## 角色边界

默认职责是“研究并整理”，不是“替用户决策”。

可以做：

- 从需求中提取会影响调研范围的场景、能力、部署和地域边界；
- 解释市场有哪些供给类型和技术路线；
- 找到相关厂商并整理产品、能力、部署、商业模式和公开入口；
- 对齐不同厂商公开资料中的同类信息；
- 区分已公开、部分公开、本次公开扫描未见和待核验；
- 汇总公开价格、计费模式、风险信号、趋势和来源。

默认不要做：

- 输出“采购结论”“推荐名单”“优先推进”“暂不建议”；
- 给厂商排名、打分或高/中/低适配度；
- 擅自形成 Short List、决定先联系谁或安排采购动作；
- 把公开资料较多等同于产品更好；
- 把供应商声明写成已经验证的事实；
- 为了显得完整而推断价格、客户、资质或产品能力。

若用户另行要求“评估、推荐、筛选、Short List、选哪家、下一步怎么做”，先完成并冻结本 Skill 的中立事实层，再交给独立的决策任务；不要把判断字段回写到本 Skill 的数据或 HTML。

## 工作流

### 1. 确定研究范围

读取用户正文、附件和上下文，整理：

- 采购对象和使用场景；
- 关键能力需求和验收指标；
- 地域、部署、数据、安全与合规边界；
- 现有系统、接口、实施和运维条件；
- 扫描范围与尚未明确的信息。

只提取会影响市场边界的信息。不要擅自补预算、规模、SLA 或技术参数。

### 2. 梳理市场结构

根据当前品类动态识别供给类型和技术路线，例如平台、垂直产品、原厂生态、SaaS/API/SDK、私有化、集成服务、开源或替代方案。

对每类信息只说明：解决什么问题、常见产品形态、适用边界和主要取舍。不要借市场分层暗示优劣或推荐顺序。

### 3. 建立厂商信息池

覆盖扫描边界内有研究意义的头部、垂直、区域、生态和替代玩家。去重集团、品牌、产品、代理商和交付主体，并核验产品仍在维护、官网/产品页/商务入口可访问。

每家统一整理：

- 供应商、产品/方案和所属供给类型；
- 产品形态、部署方式和集成方式；
- 公开资料明确覆盖的需求；
- 已公开的能力与商业模式；
- 本次公开扫描未见或仍需核验的信息；
- 证据状态、来源和商务入口。

执行地域强约束：

- 默认面向中国大陆采购场景时，大陆企业必须占候选池严格多数，海外企业只补充大陆供给不足的专项能力、技术路线或市场参照；
- 以产品能力主体或主要履约主体的注册地判断企业地域，不以中文官网、代理商、渠道或中国区销售入口替代主体判断；
- 每家记录 `enterprise_region`、地域判断依据和对应来源；主体不清时标为“主体待核验”，不得猜测为大陆企业；
- 同一市场层与厂商卡均按“大陆企业 → 海外补充 → 主体待核验”展示；Long List 必须在全表范围先连续展示全部大陆企业，再展示海外补充和主体待核验，并在每个地域组内按市场层排列。这是用户给定的地域展示规则，不是能力排名或采购推荐；
- 若品类客观上无法形成大陆企业严格多数，不得虚构厂商；必须在地域覆盖例外中说明缺口及证据，并显著展示该例外。

厂商信息池是唯一事实源。不要再复制一套“重点厂商卡片”或推荐表。

### 4. 整理商业信息

区分：

- `公开价格`：厂商或权威渠道明确标价；
- `行业估算`：由公开信号推导，必须说明假设；
- `需询价`：本次未获得可靠公开价格。

记录币种、计费单位、产品层级、区域、适用条件、一次性/持续性成本和 TCO 驱动。没有依据时直接标记“需询价”，不制造伪精确数字。

### 5. 整理风险与不确定性

只记录与当前需求有关的客观风险信号和信息缺口，例如数据出域、主体关系、产品维护、上游依赖、API/SDK 开放度、容量或许可边界。

写清：已观察到什么、为何与本需求相关、还需要获得什么信息。不要据此自动作出入围或淘汰结论。

### 6. 建立证据台账

优先使用监管机构、标准组织、政府公示、厂商正式资料、公开财报、招投标、产品文档和可核验案例。将事实、供应商声明、分析归纳、估算和参考材料分开。

## 默认交付结构

默认采用“先建立市场坐标，再沿坐标展开信息”的叙事顺序。这个顺序依次回答：研究的是什么 → 市场有哪些解法 → 每类有哪些厂商及公开信息 → 商业、约束、趋势和风险信号是什么 → 全部厂商如何索引与追溯。不要把页面做成摘要式仪表盘，也不要先抛出供应商总表。

### 1. 研究对象与扫描元信息

首屏只呈现标题、一句话采购对象、研究时间点、大陆/海外厂商数量、市场层数和简短地域/部署边界。一句话采购对象控制在约 80 个汉字内；长边界、完整需求和待确认信息放入折叠区，不让首屏承担正文。

### 2. 市场分层总图

先用一张可点击的市场全景图同时回答“有哪些解法、每类有哪些玩家”。每层直接显示供给类型、一句话解决的问题、常见形态、已识别厂商数，以及按“大陆企业 / 海外补充 / 主体待核验”分行的厂商名字。分类必须随品类动态产生；层级编号和颜色只用于定位，不表示优先级、适配度或成熟度。色带宽度可以表示本次识别厂商数量，但必须显式说明，不得装饰性模拟排名金字塔。

技术路线作为市场分层图下方的次级、默认折叠横向说明，呈现构成方式、涉及条件和已知取舍，不另起一套重复的供应商分类，也不阻断“市场图 → 分层厂商”的主线。

没有形成可核验技术路线时不显示空路线模块；没有与采购边界相关的约束或趋势时，对应独立章节和导航也不显示。价格与风险属于完整市场调研的必要信息：没有公开价格时仍需记录“需询价”，风险不足以定级时仍需记录具体信息缺口。

### 3. 按市场层展开供应商

严格沿市场全景图的顺序逐层展开，并在同层先展示大陆企业。厂商卡主视图只保留：供应商与产品、企业地域、证据状态、公开覆盖摘要、少量能力标签、部署/数据摘要、价格状态和一个关键待核验项。完整能力、部署/接入、商业口径、地域依据、全部信息缺口和来源放在同卡展开区。不要加入推荐理由、星级、适配度或“下一步”。

信息量按规模自适应：1–6 家时卡片直接展开、Long List 默认折叠；7–18 家时市场层可折叠但默认展开、Long List 默认折叠；19 家以上或市场层达到 6 类时，市场层默认折叠、Long List 默认展开。点击市场图、导航或 Long List 厂商链接时，必须自动展开对应信息。该行为只降低阅读负担，不删除数据。

### 4. 价格与计费信号

在读者看懂市场供给之后，再整理计费模式、公开价格、行业估算、需询价项、成本构成和口径局限。公开价格与估算必须明显区分。

### 5. 采购约束与合规边界

只呈现会改变供给边界的信息，例如部署、数据出域、地域、许可、主体或行业合规要求；不要泛化罗列法规。

### 6. 技术与市场趋势

趋势仅在有可靠证据且与本品类有关时展示；描述“发生了什么、可能影响什么”，不替用户制定策略。

### 7. 风险与信息缺口

汇总已经观察到的风险信号、与需求的关系和仍需补充的资料。不要给风险打分或输出采购动作。

### 8. Long List 与来源

最后用完整表格收拢全部厂商，作为全景索引而不是第二套分析。只保留分类、供应商、企业地域、产品/方案、产品形态、证据状态和商务入口；每个市场层仍按大陆、海外、主体待核验排序。公开能力与信息缺口留在上方卡片，避免重复。完整来源作为表后可展开台账。

## 信息压缩规则

- 同一厂商可在所属市场层卡片和 Long List 索引中各出现一次；Long List 不重复卡片全文；
- 同一事实只呈现一次，其他位置引用来源；
- 市场全景图允许重复供应商名称，因为名称在这里承担“玩家索引”而不是第二份事实描述；
- 厂商能力使用短句，不写公司百科；
- 单条信息缺口必须具体，不使用“需进一步沟通”等空话；
- 主视图用来源徽标就近追溯，来源标题、日期、类型和定位信息放在完整台账；
- 主视图只保留能回答“谁、做什么、怎么部署、价格状态、缺什么”的信息；每项能力、每条信息缺口、完整字段原文、企业地域依据和所有来源都必须在可展开区域或来源台账中可恢复；
- 超出主视图的信息折叠，不因压缩而删除事实或来源；
- 不显示装饰性指标、评分雷达图、推荐色阶或“成功结论”。

## 表达与证据规则

- 厂商官网和产品文档使用“供应商公开资料显示”或等义表达；
- “本次公开扫描未见”不等于“厂商没有”；
- 证据状态只描述信息可得性，不评价产品质量：`有公开资料`、`部分公开`、`公开资料不足`；
- 横向对比必须对齐同一字段，不把字段缺失自动解释为能力缺失；
- 企业地域依据优先使用工商/监管公示、厂商正式主体说明或可核验签约主体资料；产品品牌来源国与中国区实际签约、履约主体必须分开；
- 价格必须记录查询日期、币种、单位、版本/层级、区域和条件；
- 不臆造联系人、邮箱、客户、资质、市场份额或报价。

## HTML 交付

用户明确要求 HTML，或信息量较大不适合聊天阅读时，完整读取 [中立市场调研数据规范](references/market-intelligence-schema.md)，构造 UTF-8 JSON，然后运行：

```bash
python scripts/render_sourcing_report.py market-research-data.json --output "市场调研信息整合-<品类>-<YYYYMMDD>.html"
python scripts/qa_sourcing_report.py "市场调研信息整合-<品类>-<YYYYMMDD>.html" --data market-research-data.json
```

修改 Skill、数据规范、模板或渲染器后，先运行 `python scripts/self_test.py`。如有代表性的旧版 JSON，再加 `--legacy-sample <path>` 回归兼容性。

HTML 必须：

- 导航严格按“市场分层 → 各市场层 → 价格 → 约束 → 趋势 → 风险 → Long List”排列；没有可核验内容的可选约束、趋势或技术路线模块直接省略；
- 首屏保持一屏内可读，只放一句话研究对象、时间、市场层数、大陆/海外厂商数量和简短地域边界，不输出推荐结论或摘要式 KPI 面板；
- 第一块主体必须是可点击的动态市场全景图，并直接列出各层大陆与海外玩家；随后按同一分层顺序展开供应商卡片；
- 价格、约束、趋势、风险后置，Long List 收尾，来源台账放在表后；
- 不出现 Short List、优先推进、适配度评分或下一步动作；
- 证据状态只表示公开资料可得性；市场层的颜色和编号不得暗示高低排序；
- 大陆企业必须在同层卡片中先于海外企业展示，并在 Long List 全表连续置顶；企业地域必须有依据，地域标签不得伪装成能力评价；
- 根据厂商数切换“厂商卡片 / Long List”的默认展开方式，避免两套全量信息同时摊开；
- 所有被摘要的信息必须能展开查看全文；
- 为单文件离线 HTML，支持移动端、键盘焦点、打印和减少动效；桌面与移动端均不得横向溢出。

## 特殊分支

- 用户只要求解读需求时，停止在研究范围和信息缺口，不做市场扫描。
- 无法联网时，不凭记忆补齐市场；仅整理用户材料和可核验的已有资料，并明确研究覆盖受限。
- 小型演示或结构回归必须在标题和扫描范围中明确写“节选 / 非完整市场扫描”，不得把演示样本伪装为市场全景。
- 用户随后明确要求推荐时，复用已核验数据并开启独立决策任务，不回写或篡改原始研究事实。

## 完成门槛

提交前确认：市场供给结构清楚、市场图直接出现玩家、大陆企业占候选池严格多数且先展示、海外企业仅作补充、企业地域可追溯、同类信息可横向查看、价格信号有来源、未知信息被明确标记。若市场客观供给不足，地域覆盖例外必须显著披露。HTML 交付必须通过 `qa_sourcing_report.py`；Skill 变更必须通过 `self_test.py`，并至少用 1 家小样本和 19 家以上大样本验证展开策略。完成门槛不包含推荐、排序或采购结论。
